# 数学讲解流水线 — 项目说明文档

本文档用通俗语言说明：这个项目是做什么的、为什么这样设计、这样设计能带来什么好处。

---

## 一、这个项目是做什么的？

**一句话**：你给一道数学题（文字或拍题照片），系统自动生成**带旁白讲解的动画**，帮你「讲」这道题。

### 能做什么

- **输入**：题目文字，或者上传题目图片（手写、打印都可以）。
- **输出**：**Manim 视频（MP4）**。系统按 Tutor 流水线（数学分析 → HTML 可视化 → 分镜 → TTS → 脚手架 → Manim 实现 → 渲染）生成带旁白的讲解视频，适合做课件、分享或直接播放。

也就是说：**从「题目」到「可播放的讲解视频」**，全自动完成，不需要你手写脚本或剪辑。

### 谁会用得上

- 老师：快速把一道题做成可播放的讲解素材。
- 学生：看不懂答案时，看动画+听讲解更容易理解。
- 做教育内容的人：批量把题目转成动画或视频。

---

## 二、整体是怎么「跑」起来的？

可以把整条链路想成一条**流水线**（Tutor 流水线），分多步依次执行：

1. **理解题目**  
   若是图片，先用**多模态大模型**识别文字和公式，再做公式校验；然后让 AI 做数学分析（已知条件、推导事实、图形构建方法、结论等）。

2. **HTML 可视化**  
   根据数学分析，让 AI 生成 HTML+SVG 的画图过程，用于后续分镜与 Manim 实现的参考。

3. **分镜脚本**  
   生成分镜设计（每幕画面、字幕、读白、动画）以及音频生成清单。

4. **TTS 与时长**  
   用 TTS（语音合成）为每幕旁白生成音频，并测出每段时长，供 Manim 对齐画面与配音。

5. **脚手架与 Manim 实现**  
   根据分镜和脚手架，让 AI 补全 Manim 脚本（几何计算、每幕动画与 `add_sound`），再进行检查与自愈。

6. **渲染**  
   调用 Manim 渲染出 MP4 视频。

所以：**题目 → 数学分析 → HTML 可视化 → 分镜 → TTS → Manim 实现 → 渲染**，一步接一步，得到最终讲解视频。

---

## 三、为什么这么设计？

### 1. 为什么要分成「数学分析 → 可视化 → 分镜 → TTS → Manim 实现 → 渲染」多阶段？

- **分工清晰**：  
  「先理解题、再设计可视化与分镜、再写 Manim 代码、再配音、再渲染」和人类做讲解视频的流程一致。每一阶段只做一件事，AI 的 prompt 更单纯，效果更稳定。

- **便于调试和迭代**：  
  出问题时能快速判断是「数学分析不对」「分镜不合理」还是「Manim 代码或渲染有问题」，不用在整坨逻辑里乱找。

- **可复用**：  
  数学分析、分镜等中间结果可以单独查看或复用到其他输出形式，避免重复分析题目。

### 2. 为什么有「HTML 可视化」再「分镜」再「Manim 实现」？

- **HTML 可视化**：先让 AI 用 HTML+SVG 把「要画什么、怎么画」表达出来，轻量、易检查，方便和原题对照。
- **分镜**：把讲解拆成「幕」，每幕有画面、字幕、读白、动画设计，并产出音频清单，方便 TTS 和 Manim 对齐。
- **Manim 实现**：在分镜和脚手架的约束下，让 AI 补全 Python 代码（几何计算、每幕动画与配音），再渲染成 MP4。这样分步做，比一次性从题目直接生成整份 Manim 脚本更稳、更易自愈。

### 3. 为什么支持「上传题目图片」并且还有「公式校验」？

- 很多使用场景是「拍题」或「手写题」：直接给图比手打题目更方便。
- 多模态大模型有时在公式、符号上会出错；多一步「公式交叉验证」（对比原图与识别结果，用多模态模型修正），能明显减少公式写错、漏符号等问题，提高后面步骤的准确性。
- **历史标题**：上传图片时，生成记录列表中的标题会显示为**图片文件名**（如 `题目.png`），便于区分多条记录；OCR 识别出的题目文字仅用于流水线与重新生成，不会覆盖该标题。点击「重新生成」时，新记录也会沿用原记录的标题（即仍显示文件名）。

### 4. 为什么要做「断点与重试」？

- 流水线里会调外部服务（LLM、TTS 等），网络超时、限流、偶发错误很常见。
- 若某一步失败就整条重跑，既费时间又费钱。所以每步成功后都**写检查点**，失败后可以从「上一步完成之后」继续重试，不用从「题目分析」再跑一遍。

这样设计是为了：**省时、省钱、提高成功率**。

### 5. 为什么有「自愈」（Manim 自愈）？

- AI 生成的 Manim 代码有时会报错（语法、渲染错误）。
- 与其直接判失败，不如把**错误信息反馈给 LLM**，让它根据报错修改代码再试。这就是「自愈」：在限定次数内自动修错、重试，很多小问题能自动解决，减少人工介入。

### 6. 为什么用「异步任务 + 轮询状态」的 API？

- 生成一条讲解动画/视频可能要几十秒甚至几分钟，如果接口一直不返回，容易遇到网关超时（如 504）。
- 所以设计成：**提交任务后立即返回 task_id**，生成在后台执行；前端通过 **GET /api/tasks/{task_id}** 轮询状态，完成后从 `result_url` 取播放地址或下载链接。这样网关只需给「提交」和「短查询」留短超时，长耗时在后台跑，不被中断。
- 轮询与历史接口会返回**各步骤执行时长**：每步完成后立即写入数据库，界面与历史记录中都会展示（如「第1步 52.7s, 第2步 1m 9.2s」），便于排查慢步骤或做统计。

## 四、这样设计带来的好处（小结）

| 设计点 | 好处 |
|--------|------|
| **多阶段流水线** | 逻辑清晰、易排查问题、中间结果可复用。 |
| **分步实现（可视化 → 分镜 → Manim）** | 先定「要做什么」再写代码，生成更稳、出错易定位、利于自愈。 |
| **图片输入 + 公式校验** | 支持拍题/手写题，公式更准，体验更好。 |
| **断点与重试** | 失败后从断点继续，省时省成本，成功率更高。 |
| **自愈（Manim）** | 渲染/代码小错误由 LLM 自动修，减少因小错导致整条失败。 |
| **异步任务 + 轮询** | 避免长耗时请求被网关掐断，前端可做进度展示；步骤执行时长持久化并在历史中回显。 |
| **图片上传标题为文件名** | 历史列表中图片任务显示文件名，重新生成后标题保持不变。 |
| **配置与 Prompt 可调** | 模型、超时、自愈次数、动画风格等都可配置，便于适配不同环境和口味。 |

## 五、和「直接用 AI 生成整段视频」相比呢？

- **一步到位生成整段视频**：对模型要求高、容易前后不一致、难以分步修某一环节。
- **本项目的做法**：把「理解题 → 可视化 → 分镜 → Manim 实现 → 配音 → 渲染」拆开，每步有明确输入输出和检查点，可控、可修、可重试，且能复用中间结果（如同一道题换风格再出一版）。

通俗讲：**不是让 AI 一口气「变」出一段视频，而是让 AI 按流程一步步「做」出来**，这样更稳、也更好维护。
